Harness methodology · 19 August 2026

Structured User Story Driven Development

How to make LLM-assisted changes governable, reviewable, and reusable — by treating the user story, not the prompt, as the first-class delivery artifact. This is the method the Claude Harness Engine runs end to end, and the deep design of how that loop is wired.

Companion to Structured Prompt-Driven Development In-repo name: SSDD Doctrine: plan-review-loop/references/ssdd.md

Once a team adopts AI coding assistants, the first gains show up at the individual level: one developer can draft, modify, and refactor code much faster than before. Delivery speed is rarely limited by typing. When you look at the full lifecycle, from requirements through release, new friction appears.

  • Ambiguous requirements become code quickly, and misunderstandings scale with them.
  • Reviews have to process more change, and inconsistency becomes easier to introduce.
  • More integration and testing issues surface because “generated” does not mean “aligned.”
  • Production risk is harder to reason about when the volume of change rises.
  • Chat transcripts vanish. The next session cannot tell what was decided, only what landed in git.

Local speed improves. That does not automatically become system-level throughput. It is the Ferrari-on-muddy-roads problem Zhang and Xia describe in SPDD: the engine is powerful, arrival time is determined by the road. The real question is not “how do we generate more code?” It is how we make AI-generated changes governable, reviewable, and reusable so teams get faster and safer.

Thoughtworks Global IT answered that with Structured Prompt-Driven Development: version the prompt, review the prompt, generate from the prompt, and when reality diverges, fix the prompt first. That is the right closed loop. SUDD keeps the loop and changes the artifact.

When reality diverges, fix the structured story record first — then re-render, then the code.

What is SUDD?

Structured User Story Driven Development is an engineering method that treats the user story — joined into a machine-checkable bundle — as the first-class delivery artifact.

Instead of relying on ad hoc chats, and instead of maintaining a parallel library of REASONS prompt files, SUDD turns each ready story into an asset that can be version-controlled, reviewed, reused, and improved over time. The story already carries requirements, domain language, scope, and acceptance criteria. Design and test planning already produce ownership, operations, and verification rows. SUDD joins those surfaces into one execution contract. Generation reads that contract. Evaluation scores the running system against it. Sync writes code-side structure back into it.

The Claude Harness Engine implements SUDD as Structured Story-Driven Development (SSDD). The names refer to the same method. This essay uses SUDD because the unit is the user story; the repo, skills, and changelog say SSDD.

Intent

Story + Generation Contract

Given/When/Then ACs, scope out, entities, operations, cited safeguards. Human-readable ticket stays in specs/stories/.

Join

Story bundle

specs/bundles/{id}.json is the executable contract. /auto and /implement load the bundle, not the artifact pile.

Constitution

System REASONS Canvas

reasons-canvas.md is the living design for the whole system. Per-story contracts are deltas against it, not replacements.

Loop

Closed on two scales

Inside an iteration: record → code → evidence → sync. Across iterations: the next story starts from the sealed pack, not a blank chat.

SUDD has two core components, mirroring SPDD’s canvas-plus-workflow split — but the grain is different.

What SUDD adds to SPDD

Same closed loop. Same REASONS shape. A different first-class artifact, and a control plane SPDD leaves to human review.

Sidebar · What SUDD adds to spec-driven development

If you already know spec-driven development, you will recognize the starting point: write the spec clearly first, then let the model implement. SPDD takes a spec-anchored angle and treats structured prompts as governed team assets. SUDD is also spec-anchored, but it refuses a second prompt library. Planning already writes stories, design, and tests. The missing piece was the join that generation is forced to execute — plus deterministic sensors that prove the join is still honest.

SPDD

Prompt as artifact

A versioned REASONS file per change. Commands extract analysis, write the canvas, generate code task-by-task, update the prompt when requirements change, and sync the canvas when code is refactored. Honesty of the artifacts is largely human review.

SUDD

Story as artifact

A versioned story bundle per ready story. Human gates shape decisions; scripts write volume; sensors hard-block missing IDs, pending operations, canvas drift, and untraced tests. The system canvas stays the constitution; the generation contract is the per-change delta prompt.

The gap analysis that produced this adaptation said it plainly: this harness was already ahead of the SPDD example on behaviour verification and on deterministic grounding. What it lacked was the living, code-synced design artifact and a single join at story grain. SUDD is that join. It does not import openspdd. Importing the CLI would have duplicated /brd, /spec, and /design and split the pipeline.

The story bundle

One JSON file per ready story. A deterministic join, not a new planning phase, and not a prompt the model is free to paraphrase.

Planning already writes stories, design, and tests into specs/. Without a join, /implement can still load a story file and improvise against chat. Design and the test plan are then documentation the generator is not forced to execute. The bundle closes that hole.

buildBundle() in .claude/hooks/lib/story-bundle.js is a pure function. Callers pass already-read objects; I/O lives in bundle-write.js and bundle-check.js. That split is load-bearing. Integration tests must round-trip the real writer through the real checker. A hand-built fixture that encodes the wrong shape keeps every test green while the feature is inert.

Two readiness modes

The same checker has two floors, because planning and generation need different honesty.

  • skeleton — written at spec-render. ACs must exist. Operations may still say pending. The bundle is a placeholder so later phases have a join target.
  • implementable — required before /implement and /auto spawn anyone. Operations must name repo-relative files. Verification-matrix rows must exist. Owned files or Operations paths must exist. When a BRD acceptance spine exists, every test that cites a story AC must also cite an original-requirement id.

Dormant when there are no ready stories: the checker exits 0 rather than failing an empty greenfield. A missing bundle for a ready story is a hard block.

The generation contract is the delta prompt

The system canvas is too coarse to be the per-change generation prompt. Each story carries a ## Generation Contract with four subsections — Requirements, Entities, Operations, Safeguards — the R / E / O / S slice of REASONS at story grain.

  • Requirements keep the story’s Given/When/Then AC ids. They are not rewritten.
  • Entities are marked existing | new | unknown, citing a code-graph path when the repo is brownfield.
  • Operations are ordered steps that each name a file. pending is legal at skeleton, illegal at implementable.
  • Safeguards cite SG-n ids the story can violate, or none plus a reason of at least 25 characters.

Behaviour changes update the Generation Contract first, rewrite the bundle, then touch source. A teammate that codes from chat while Operations still say pending is the failure this gate exists to stop.

The REASONS constitution

SPDD’s seven-part canvas is kept — as the system design, not as a per-story prompt file.

Zhang and Xia’s REASONS Canvas forces clarity from intent through governance: Requirements, Entities, Approach, Structure, Operations, Norms, Safeguards. SUDD keeps that shape in specs/design/reasons-canvas.md, emitted by /design and validated by validate-canvas.js.

Figure 1. REASONS stays the system constitution. Story grain lives in the Generation Contract and the bundle.

Two extra rules make the canvas a sensor target rather than an essay:

  1. A machine-read Governs list names the source paths the canvas claims to own. Empty Governs is a structure failure.
  2. When brd-safeguards.json exists, every SG-n the BRD recorded must be cited in Canvas Safeguards or Norms. UNCOVERED (a required constraint the design does not carry) and UNKNOWN (a cited id absent from the spine) both block. A misplaced citation is a warning: the constraint reached the design; only the filing is off.

Approval flags change whether a human must stop at the planning gates. They do not turn off machine gates. Default /build is gated. --autonomous reduces approval. --auto waives planning approvals and records the waiver. Headless lanes waive; they do not skip silently. Merge stays human-owned.

Deep down: the artifact spine

Every downstream id is grounded in an upstream id. Relative checks are not enough; the spine also has an absolute floor.

SPDD’s worked example produces rich analysis and a precise canvas, then relies on people to notice a missing acceptance criterion or an invented domain term. SUDD encodes that honesty as a chain of hard-blocking sensors. A green pipeline is not “the model said the BRD is complete.” It is “these identifiers still join.”

  1. PRD — the only artifact a human authors from scratch. validate-prd.js requires every functional requirement to carry an observable postcondition. Ids are load-bearing; heading text is not.
  2. BRD adopt — default /brd --prd is adopt-only. prd-extract.js plus brd-adopt.js carry PRD text verbatim into brd-requirements.json. There is no rewriting step that might incidentally “fix” a malformed requirement.
  3. Taxonomy floor — brd-taxonomy-check.js is the only absolute check in the planning chain. Ten slots (functional, data lifecycle, integration, performance, security/authz, privacy/retention, observability, operability, UX/accessibility, constraints) each need a tagged requirement or a substantive na_reason. Placeholder excuses fail. Relative grounding cannot catch a silent FRD that stayed silent all the way down.
  4. Spec decisions — a human chooses milestone scope, epic boundaries, and real-versus-defensive dependencies before generation. At least one decision must have basis: "human". Load-bearing decisions cannot be “original planner reasoning.”
  5. Stories — INVEST scorecard, typed dependency edges (contract | data | behavior | ui), Given/When/Then ACs with stable ids, scope in / scope out. Independence is computed from ownership clusters, not self-graded.
  6. Design decisions — a load-bearing architecture decision must name what it rules out. n/a / none / TBD are rejected. Trace-check can pass and the canvas can be well-formed while every decision is still a preference an implementer can quietly reverse.
  7. Test traces — each case maps to a story AC and, when the spine exists, a BRD acceptance id. features.json steps are generated from the Given/When/Then triple, not re-authored.
  8. Plan approval — plan-approval.js records that a human reviewed the pair, with a sha256 of the approved artifacts. An approval is void once those artifacts change. That is the load-bearing anti-rubber-stamp property.
  9. Plan seal — plan-seal.js freezes the pack /auto is allowed to read, including specs/bundles/.

Two graphs sit on the same stories and answer different questions. dependency-graph.json is topological depth — scheduling order for waves. story-clusters.json is ownership: weakly connected components over hard edges only (data, behavior). Contract and UI edges are cuttable because publishing the interface first genuinely parallelizes two engineers. An interface contract with contract_story: null is a hard failure: the cut is fiction.

Deep down: deterministic join

Models write judgements. Scripts write volume. Sensors prove the join.

This is the most important mechanical idea in the harness, and the one most often missed if you only read the skill prose.

A planning skill that dumps every story file, the BRD, the eval JSON, and the canvas into one context window will spend its budget re-reading what a script already knows. SUDD therefore splits each gate into shape (human + model, small) and render (deterministic writer, large).

  • spec-render-write.js expands stories.json into story files, features, traces, clusters, and skeleton bundles.
  • test-plan-write.js emits the matrix, traces, and a skeleton plan from story-traces.json in one process.
  • bundle-write.js joins ACs, ownership, matrix rows, generation contract, and originating BRD acceptance.
  • design-render orients from stories.json, not every E*-S*.md.

After design, bundles are re-joined so Structure and owned files land before /test. After implementation, spdd-sync.js --write applies Canvas Governs/Operations stubs and bundle ownership, then reports what is still wrong. Report-only without --write.

The join sensors are not optional ceremony at the end of /auto SECTION 5. They sit in GATE_CATALOG, the same list the git hook runs: generation-contract, story-bundle-check, canvas-sync-check, and (when claude-progress.txt has a current group) impact-scoped regression. Skipping SECTION 5 still fails the commit.

Deep down: guides, sensors, cadence

Agent = model + harness. The model writes code. The harness is everything around it that makes the output trustworthy.

HARNESS.md is the human registry; harness-manifest.json is the machine inventory. A control is not implemented merely because a script exists. Status, wired_at, cadence, and scope must match real execution.

Guide · feedforward

Steer before the act

Skills, the canvas, the bundle, learned rules, process rules, code-gen principles. Prevents a class of mistakes from being attempted.

Sensor · feedback

Observe after the act

Computational (types, coverage, ID joins), inferential (reviewers), or hybrid. Feeds self-correction. Feedback-only repeats mistakes; feedforward-only encodes untested rules.

Four axes

What is governed

Maintainability, architecture, behaviour — and traceability, which the source articles leave to humans and this harness hard-blocks.

Earlier is cheaper. Grounding fails before code exists. Session hooks fail before a bad edit is even written. pre-write-gate.js blocks prohibited paths, prompt-prefix files, secrets, and selected TDD/coverage violations. pre-bash-gate.js closes the shell-write bypass and rejects destructive git during parallel implement. Commit runs the tiered registry. Integration runs the evaluator against a live app. Drift runs outside the change cycle so rot is visible even when nobody opened a PR.

Sensor tier is a runtime dial, not a SKU. minimal / standard / strict come from HARNESS_SENSOR_TIER or project-manifest.json#quality.sensor_tier. standard is the product default. strict adds cycle, coupling, clone, and mutation ratchets when the graph is present.

The harness also ratchets itself. control-budget-gate.js treats the count of registered controls as monotonic: the count may only stay flat or drop unless a new control carries a written net_add_justification. Companion reports nominate shelfware. A preventive gate that never fires looks identical to a dead one; canaries feed each detector a known-bad and a known-good input so “never blocked” splits into proven-live versus unproven.

Deep down: generate from the join

After the plan seal, /auto is /spdd-generate. Teammates receive the bundle, not the pile.

Reloading /brd, brd.md, or every story file inside generate is both a token leak and a drift source. The sealed pack already joined those facts. The orchestrator:

  1. Recovers context from claude-progress.txt, features.json, and git. On a fresh process it runs a resume smoke check before building (the Anthropic long-running-agent failure mode: do not assume the app still boots).
  2. Negotiates a sprint contract per group from the bundle’s ACs, owned files, and matrix ids.
  3. Validates every ready story at --mode implementable.
  4. Spawns one implementer per story for multi-story groups (cap five concurrent), injecting learned rules, process rules, CONTEXT.md, and a context pack when a real code-graph exists.
  5. Runs the ratchet: tests, run-gate-checks.js, story-sync, then the join sensors.
  6. On PASS, updates features and continues. On FAIL, self-heals within a bound (three consecutive failed heals marks the story BLOCKED, extracts a learned rule, and moves on). A 50-iteration hard stop and a wall-clock / spawn / cost budget prevent oscillation without convergence.

File ownership is not a suggestion. The bundle’s structure.owned_files is the assignment. Teammates may not edit outside it without coordinator approval. Shared types use an explicit handshake. Parallel implement also flips HARNESS_PARALLEL_AGENTS, which makes stash, reset --hard, clean -fd, and force-push denied in the bash gate.

Testing discipline is a manifest knob, not a hidden default:

  • outcomes — tests and production code together at the named seams. Default on new scaffolds.
  • tdd — write-lock, red-phase recorder, test-integrity. A test file that is still red cannot be edited; a test that changed between the red run and the green run fails at commit.
  • at-first — business-readable Given/When/Then against a Ports-and-Adapters seam, with a red receipt, before production files for that story.

First-window initialization is split from later windows. The first context window sets the workspace; later windows resume. Session chaining writes durable state so a killed process loses nothing that was committed. /status reads that state, including bundle count and last-sync age.

Deep down: the writer / grader split

The implementer is never the authority for its own result. That is not a style preference. It is the anti-psychosis rule.

SUDD would still be useful with only the planning join. The harness goes further because generated code that “looks right” in the builder’s transcript is the most expensive kind of wrong. The evaluator, code-reviewer, and security-reviewer run in fresh context. They receive the contract, the diff, and the sealed stories — not the builder’s reasoning.

Three runtime layers, then security

  1. API — live HTTP against the sprint contract. Status, body contains, optional schema ref into api-contracts.schema.json.
  2. Playwright — semantic locators, real user path. Evidence ledger required. Satisfying a functional check via browser_evaluate is a block: that proves a script ran, not that a user can do the thing.
  3. Design / vision — Full mode only, scored on a weighted rubric with a floor per criterion. Never an unstructured “looks good.”

Security is a gate, not advice. A missing scan is a fail. On a security-boundary diff, /gate can spawn three independent evaluator instances and three security-reviewer instances and majority-vote per axis so no single blind spot decides.

Review itself is tiered. Default is one reviewer with two axes (standards vs spec). Size, a security boundary, or sensor_tier=strict flips to two independent reviewers whose verdicts merge under union: any BLOCK fails. The builder transcript is excluded from the review pack on purpose.

Ratchets, not absolute sermons

Several sensors compare to a committed baseline and only fail on regression: coverage, cycles, unstable hubs, clone clusters, performance p95, agent-readiness pillars, security findings (except secrets — new secrets always block), and the harness’s own control budget. First measurement is often a warn that establishes the baseline. Laundering a regression by refreshing the baseline on FAIL is forbidden.

Local iteration uses impact-scoped regression (deterministic test impact analysis over code-graph.json). Merge time runs the full accumulated Playwright suite plus prior groups’ sprint-contract API checks, with replay so a missing boundary fixture is a hard fail rather than a live external.

Deep down: two-way sync

SPDD’s golden rule, implemented as two flows and a fail-closed AC check.

Behaviour change

Record first, then code

New rule, new field, new invariant: edit the Generation Contract, design-decisions.json, or the Canvas, rewrite the bundle, then generate a targeted diff. This is SPDD’s /spdd-prompt-update. Do not patch api-contracts.md and leave the canvas stale.

Refactor

Code first, then sync

Structure or style that does not change observable behaviour: change the code, then spdd-sync.js --write and /story-sync. Owned-file moves update Structure and Canvas Governs. AC drift fails closed — update the story and run bundle-write; do not silently rewrite acceptance.

Sync is split on purpose. Path sync (canvas-sync.js) is deterministic: it proposes the exact Governs bullets and Operations stubs the diff implies, and --write applies them. Semantic sync (does the prose still hold?) is a companion sensor. Full bidirectional regeneration of the entire canvas from the tree was deferred by choice. Detection plus “fix the record first” shipped. That is enough to stop silent rot; it is not a claim that the canvas is a compiler.

Deep down: token discipline

SUDD is also a cost architecture. Unstructured “read everything, then think” is how planning burns a day’s budget before code exists.

  1. Shape, then /clear, then render. Judgement stays in the main session. Volume forks. Same-session render re-bills the dialogue.
  2. Digest, do not dump. phase-digest.js is the shaping input. Do not read brd-requirements.json, every story file, or eval JSON whole.
  3. Scripts write volume. The model fills only what a script cannot — seams, contested forks, Operations that name files.
  4. Review the lean pair in lean-review-surface.md, not the artifact pile. Phase-eval is --eval only.
  5. One structured record per gate. A change request edits that record, then --render-only. Re-present a changelog. Declined feedback is recorded, not silently absorbed.
  6. Do not churn the cached prefix. Mid-session writes to CLAUDE.md, .mcp.json, and settings are blocked. Model swaps happen on subagents, never by switching the orchestrator mid-run.

Progressive loading on /auto is the same idea at generate time: the skill file is an index. The orchestrator loads only the section it is executing. Wiring tests scan the index and the section files as one corpus so the split cannot drift.

Deep down: brownfield and reuse

Most work is enhancement. SUDD is designed for a living tree, not only for a greenfield first sprint.

Before broad planning or feature work in an existing codebase, /brownfield builds a factual map: architecture, tests, risk, change strategy, and a deterministic code-graph. When that graph is real, generate is context-first: context-pack.js --diff --budget 1600 produces cited read_next ranges. Skeleton-flagged god files are never whole-file-read.

Existing symbols that must change are classified before the first production edit:

  • Covered — change in place; existing tests are the pin.
  • Uncovered but pinnable — write characterization tests at the nearest observable seam and prove they bite before editing.
  • Uncovered and unpinnable — sprout: add behaviour in a new fully-tested unit; the legacy file may gain at most a call line or a wrap-rename pair. A mechanical sprout-diff gate enforces the symbol cap.

Sprint N does not regenerate the living design. It grounds the new PRD against the prior requirement spine, writes a design amendment, appends matrix rows as VM-id@sN (never deletes the old row), and re-joins bundles. An amendment-provenance sensor blocks specs/design/ edits that have no matching amendment.

Reuse is gated at intake when the scout band is medium or higher, a constitution invariant is touched, or a same-release clone cluster exists. The decision and a performance budget are recorded before code. That is alignment at the “do we even build this?” layer SPDD leaves to pairing.

Where SUDD fits

SUDD is an engineering investment. The harness already encodes SPDD’s fitness table as lanes. Using the wrong lane is the usual failure mode.

FitScenarioLane
★★★★★ New product, or a large enough new scope that stories, design, and tests must be re-shaped /build → human gates → /auto
★★★★★ High-compliance / hard constraints / financial core Same, with sensor_tier=strict and security-boundary /gate
★★★★★ Next PRD on an established product /sprint (amendment, not redesign)
★★★★☆ One existing-code feature, end to end to a reviewed PR /feature → /change or the epic path
★★★★☆ Bounded behaviour change with a story or issue /change (test-first, full verification)
★★☆☆☆ Tiny low-risk fix, docs, narrowly scoped edit /vibe — micro-contract, still reviewed
★★☆☆☆ Behaviour-preserving structural work /refactor — keep refactor commits behaviour-free
★☆☆☆☆ UI mockup, ARB narrative, research report — does not ship Lite / artifact lanes. Do not run the GAN loop.
★☆☆☆☆ Domain is a context black hole; no observable postconditions Stop. Write a PRD. SUDD cannot invent the “why.”

SKU is an install boundary (harness-core, harness-full, harness-lite), separate from sensor tier. Lite is for artifacts that never ship. Small but shippable code uses /build --lite or /vibe inside the full harness, not Lite.

Worked example: enhancing a short-link service

The same shape as the SPDD billing-engine walkthrough, executed through SUDD artifacts instead of a prompt file.

Imagine a running service that already creates short links: POST /api/links accepts a URL and returns a code. Business now wants reserved aliases (“vanity codes”) for paying workspaces, with uniqueness scoped to the workspace, not global. That is an enhancement — the common case.

Step 1 — Lock the story, not the implementation

A human writes or adopts a PRD with observable postconditions. Lean /brd --prd extracts the spine and an analysis seed (domain terms, the PRD’s own questions, risks, safeguards). /spec shapes milestone scope with the human, then renders stories. For this change we get one ready story, not two accidental ones:

E2-S1 — Reserve a vanity code

In: a workspace admin can reserve an alias; collision inside the workspace is 409; other workspaces may use the same alias.
Out: no billing change, no public directory of aliases, no change to anonymous short-link creation.
AC (E2-S1-AC1): Given workspace W and unused alias launch, when an admin reserves it, then GET /w/{W}/launch resolves to the target and the record stores workspaceId=W.

The story’s Generation Contract is still skeleton: Operations say pending. That is legal. Implementable would not be.

Step 2 — Abstraction before generation

/design records decisions that name what they rule out (for example: “workspace-scoped unique index, not a global alias table”). The Canvas Entities section marks VanityReservation as new and Link as existing, citing the code-graph. Structure lists src/links/reservations.py. Safeguards cite the BRD invariant that anonymous create must not require a workspace. validate-canvas.js refuses an empty Governs list. Bundles are re-joined so owned files exist before test planning.

Step 3 — Tests as operations you can run

/test --plan-only writes matrix row VM-014 (layers: unit, API) and traces E2-S1-AC1 → BR-12-AC1. Under at-first, the acceptance test is written against the reservation port with a fake store, observed red, and receipted before any production file is added. Playwright stays the confirming layer, not the primary AT.

Step 4 — Generate from the bundle

After seal, /auto loads specs/bundles/E2-S1.json plus the cited canvas slices. Step 0.2 of implement replaces pending with ordered Operations that name files, re-validates implementable, and only then writes code. The teammate does not receive the BRD. Reviewers do not receive the builder transcript.

Step 5 — Two kinds of review fix

A missing default for historical rows that have no workspaceId is a behaviour change: update the contract (“historical links remain globally unique and cannot be reserved”), rewrite the bundle, regenerate the targeted persistence path. Extracting a magic TTL into a named constant is a refactor: change the code, then spdd-sync.js --write. Regression is impact-scoped locally and full-suite at /gate.

What the example delivered

  1. A behaviour change whose acceptance criteria still join to the original requirement ids.
  2. A living canvas whose Governs list includes the new reservation module.
  3. A bundle the next sprint can start from, instead of rediscovering the decision in chat.
  4. Evidence: AT red receipt, API check, optional Playwright path, security review of the new uniqueness rule.

Three core skills

SPDD named the human skills that actually move. SUDD keeps them and attaches a mechanical proof to each.

Alignment

Lock intent before you write code

/brd and /spec make in / out / postcondition explicit. Proof: PRD shape, taxonomy floor, spec-decisions with a human basis, plan-approval digest.

Abstraction first

Design before you generate

/design reviews types, signatures, and the call stack on the canvas before any product file is written. Proof: decisions that rule things out, canvas structure, Governs, implementable Operations that name files.

Iterative review

Turn output into a controlled loop

plan-review-loop is the bounded dialogue (cap 5). Generate uses writer/grader split, ratchets, and fail-closed sync. Proof: evaluator layers, adversarial review when the tier says so, join sensors on every commit.

A fourth skill is implicit in this harness and mostly absent from the SPDD article: leave a receipt. Coverage verdicts, AT-red, plan approval, evaluator evidence, attestations — if a discipline only lives in a skill file, an agent under pressure will skip it. SUDD assumes that, and puts a sensor on the receipt.

Trade-offs to consider

SUDD is not the shortest path to “generate code quickly.”

Closing

SPDD showed that prompts can be first-class delivery artifacts: versioned, reviewed, reused, and kept in sync with code. SUDD takes that closed loop and aims it at the artifact delivery teams already know how to argue about — the user story — then joins that story to design and tests so generation has one contract and evaluation has one oracle.

The Claude Harness Engine is the control plane around that method: human gates on the left, deterministic writers in the middle, generate-from-the-join on the right, an independent grader on the running system, and sensors at every cadence so “the skill said so” is never the only proof.

The framework in this essay is the moves. The advantage still comes from the meta-skills behind them: abstraction, systematic analysis, and a deep reading of the business. Those are human strengths. The harness exists to keep those strengths in the loop while the model does the typing.

Some questions answered

The same questions the SPDD article received, answered for SUDD.

With hooks and sensors already governing output, what gap does SUDD fill?

Both finer-grained intent and drift prevention, and they reinforce each other. Global hooks are a safety net at the wrong altitude: they cannot tell you whether this story’s Operations still name the files the teammate is about to edit. The bundle is that altitude. Sensors then prove the bundle, the canvas, and the traces still join. Neither layer replaces the other.

How is this different from CLAUDE.md plus progressive disclosure?

Project instructions are feedforward for the whole repo. They go stale the moment the code moves, and they are the wrong grain for a single change. SUDD’s record is per story, versioned with the code, two-way synced, and hard to ignore: generate will not spawn if the join is not implementable. Progressive disclosure is how the skills stay small. It is not the delivery artifact.

Does SUDD close the “why” loop automatically?

No, and that is deliberate. There is no silent learning loop that makes the model wiser across chats. The “why” is captured in the PRD postconditions, BRD safeguards, design decisions that name what they rule out, and the Generation Contract. Version control makes it durable. Two-way sync keeps it current. Humans remain gatekeepers for load-bearing calls. Automated verification is at the asset layer (IDs, structure, receipts), not a substitute for judgement.

If two developers write different contracts, haven’t you just moved the variance up a layer?

Yes, partly. The canvas and the contract narrow the band compared with free-form prompting; they do not eliminate it. What changed is the floor and the review surface. A thin contract fails implementable. A thick but wrong contract is still a human review problem — now aimed at one file instead of a chat. Automated “is this contract substantively good?” is the same remaining gap the SPDD authors named. SUDD’s extra move is traceability: a contract that does not join to ACs and matrix rows cannot ship, however eloquent it is.

Why not just keep REASONS prompt files like openspdd?

Because this pipeline already produced stories, design, and tests. A parallel prompt library would have been a second source of truth and a second place to rot. The system canvas is enough constitution. The missing piece was the join at story grain. That is the bundle.

Can I skip planning and only run /auto?

Only if a sealed pack already exists. /auto is generate. It will not reopen /brd / /spec / /design / /test. Headless /build --auto waives the human stop and records the waiver; it still runs the writers and the machine gates. There is no honest path that starts from a vibe and exits with a sealed, implementable bundle for a new product.
